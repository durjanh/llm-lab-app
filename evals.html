Lab 7 · Evals

Did the prompt get better, or did you get lucky?

An eval is a set of test cases plus a way to grade the answers. It turns "this prompt feels better" into a number you can defend. This lab builds one, grades answers three ways, then asks the question most teams skip: is the difference bigger than the noise? GPT-2 does the classifying, using its real next-token probabilities.

1. Build a labelled test set

A test set is a list of inputs, each with the answer a person agrees is correct. The task here is sentiment: is each review positive or negative? A third of the cases are deliberately hard. Sarcasm uses nice words to mean the opposite. Negation flips a word, as in "not bad at all". Mixed reviews praise one thing and criticise another, and the label is the overall verdict.

This matters because a prompt change is only as good as the cases you test it on. Leave out the hard cases and every prompt looks fine.

Good test sets come from real traffic and include the failures users reported. They keep a sensible label mix, and they stay frozen while you compare prompts. If you change the cases and the prompt at the same time, you cannot tell which change moved the score.

2. Decide how each answer is graded

A grader turns one model output into a score. Use the cheapest grader that measures what you care about. Code is free, fast and gives the same answer every time. A model judge can read meaning, but it costs money and makes mistakes of its own.

Exact match

Compare the output with the expected label as a string.

Use it for classification, extraction of IDs and dates, and multiple choice.

Watch out for formatting. "Positive." is not "positive". Constrain the output so it can only be a valid label.

Code-based rubric

A list of checks written in code: required facts, length limits, banned content, valid JSON.

Use it for free text where you can name what must and must not appear.

Watch out for wording. Keyword checks miss paraphrases and are fooled by negation.

LLM as judge

A second model reads the output and a rubric, then returns a score and a reason.

Use it for qualities code cannot check, such as faithfulness, tone and helpfulness.

Watch out for the judge's own biases. Check it against human labels before you trust it.

Exact match, strict and normalised

The expected label is positive. A strict grader fails anything that is not exactly that string. Normalising first, by lowering the case and trimming spaces and end punctuation, rescues small formatting slips. It cannot rescue a sentence.

Code graders are exact, cheap and repeatable. They are also literal, so test the grader itself on cases like these.

LLM as judge

A judge model reads the ticket, the summary and the rubric, then returns a score from 1 to 5 and a one-sentence reason. Structured outputs force the reply into that shape, so code can read it. Here a score of 4 or 5 counts as a pass.

The exact request the judge receives:

Test the judge for position bias

Show the judge two summaries and ask which is better. Then swap the order. A fair judge picks the same summary both times.

Judge pitfalls.
  • Position bias. When comparing two answers, judges often favour whichever comes first, or second. Run both orders and only count a win that survives the swap.
  • Verbosity bias. Longer answers tend to score higher even when they are worse. Put length limits in the rubric and check them with code.
  • Self-preference. A judge can favour text written in its own style. Where you can, use a judge that did not write the answers.
  • Check the judge against people. Label 50 to 100 outputs yourself and measure how often the judge agrees. Only rely on it where it agrees.
  • Keep the scale small and anchored. Pass or fail, or 1 to 5 with each score described, is more consistent than "rate from 1 to 10".

4. Is B really better? Put an interval on it

Your test set is a sample. Another sample of the same kind would give a slightly different score. A 95% confidence interval is the range of accuracy the prompt would plausibly get on other samples like yours. Here it comes from the bootstrap: build a new test set of the same size by drawing cases from yours at random, with replacement, so some appear twice and some not at all. Score it, repeat 2,000 times, and keep the middle 95% of the scores.

The difference B − A is bootstrapped in pairs. Each resample draws the same cases for both prompts, because both saw the same reviews. That is fairer and tighter than comparing two separate intervals. Differences are in percentage points: going from 70% to 75% is a gain of 5 points.

5. Run it again: run-to-run variance

So far each prompt always takes its most likely label, so a rerun gives the same answer. Real systems sample, and hosted models can vary between identical calls. Here each label is drawn at random from GPT-2's own probabilities, so a review that is 70% positive comes out positive about 70% of the time. Temperature reshapes those odds. Below 1 it sharpens them, above 1 it flattens them, and 0 means always take the top label.

This matters because one run of each prompt can pick the wrong winner. On current Claude models you cannot turn temperature down, so run each case a few times and average. These runs use the cases selected in section 4.

Engineering takeaways

  • Build the test set before you touch the prompt. Start with 50 to 200 real cases, including the failures users reported. Version it like code.
  • Grade with code wherever you can. Exact match and rubric checks are free and repeatable. Use an LLM judge only for what code cannot check, and measure its agreement with human labels first.
  • Report an interval, not a single number. "72%, 95% interval 60% to 83%" stops a team from shipping noise.
  • Compare prompts on the same cases, in pairs. Look at the interval for B − A, and count what B fixed and what it broke.
  • Size the test set for the gap you need to see. At 75% accuracy, a 95% interval spans about ±30 points with 8 cases, ±13 with 40 and ±5 with 300. Small gains need hundreds of cases.
  • Run each case more than once. Current Claude models do not accept temperature, and hosted outputs can vary. Average a few runs per case before deciding.
# Classify a labelled test set with Claude and report accuracy with a 95% bootstrap interval
import json
import random
from anthropic import Anthropic

client = Anthropic()
SCHEMA = {
    "type": "object",
    "properties": {"sentiment": {"type": "string", "enum": ["positive", "negative"]}},
    "required": ["sentiment"],
    "additionalProperties": False,
}

def classify(review: str) -> str | None:
    resp = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=4096,
        system="Classify the sentiment of the customer review inside the review tags.",
        messages=[{"role": "user", "content": f"<review>{review}</review>"}],
        output_config={"effort": "low", "format": {"type": "json_schema", "schema": SCHEMA}},
    )
    if resp.stop_reason == "refusal":
        return None  # counts as wrong
    text = next(b.text for b in resp.content if b.type == "text")
    return json.loads(text)["sentiment"]

def bootstrap_ci(scores: list[int], resamples: int = 2000, seed: int = 0) -> tuple[float, float]:
    rng = random.Random(seed)
    n = len(scores)
    means = sorted(sum(rng.choices(scores, k=n)) / n for _ in range(resamples))
    return means[int(0.025 * resamples)], means[int(0.975 * resamples) - 1]

test_set = [("Not bad at all.", "positive"), ("Oh great, it broke again.", "negative")]  # your labelled cases
scores = [int(classify(text) == label) for text, label in test_set]
low, high = bootstrap_ci(scores)
print(f"accuracy {sum(scores) / len(scores):.1%}, 95% interval {low:.1%} to {high:.1%}, n={len(scores)}")
