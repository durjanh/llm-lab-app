# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

LLM Lab: interactive pages that show how LLMs and the systems around them work. A FastAPI backend (`backend/`) proxies live Claude and Azure calls behind a spending cap; a React + TypeScript frontend (`frontend/`, Vite) has one route per lab. `README.md` is the full reference; keep it in step when routes, labs or setup change.

## Commands

Run everything from the repo root, with the virtual environment active (`source .venv/bin/activate`; use `python3` before that on macOS).

```sh
python -m backend --budget 1 --reload   # backend on 127.0.0.1:8000, restarts on changes in backend/ and python/
cd frontend && npm run dev              # Vite on :5173, proxies /api, /models, /sites/ and /site-versions/ to :8000

pytest backend                                          # all backend tests (fake Claude client: no key, no cost)
cd frontend && npm run build            # typecheck + production build into frontend/dist (served by the backend on :8000)
```

`pytest` must run from the repo root, because tests import `backend.app...`. There is no Python linter configured.

**Before you finish a change:** run the `check` skill (`/check`), then the `code-review` skill (`/code-review`) on the diff, and fix each confirmed finding with a test that recreates it. Use the default level; `max` only when asked. The tests use a fake model and send one request at a time, so they miss what review finds here: two requests at once (double clicks, two tabs polling), refusals and empty or cut-off replies, an API error part-way through a turn, and unvalidated input. Project settings are in `.claude/settings.json` (shared permissions, and a hook that runs Prettier on edited front-end files); personal ones go in `.claude/settings.local.json`, which is gitignored.

**Databases and data loads get a script in `tools/`.** A feature that creates a database, schema or index, or loads data into one, ships a script there (`vector-db.sh` starts PostgreSQL; `shop-data.sh` sets up and fills the shop; `vector-samples.sh` loads the sample documents) that someone can run on a fresh clone or a new machine, and again after changing the schema, the loader or their data. It must be safe to run again (create or bring up to date, carry on where a stopped run left off, replace rows by id), call the same backend code and read the same `.env` (no second copy of the schema or loader), work without the web server, and say what to run when Docker, the database or a model is missing. If the backend can write the same data, they share a lock in the database so they never write at once. List it in `tools/README.md` and in the README's "Data and databases" and "what to rebuild" tables, and test it the way `backend/tests/test_shop_data_tool.py` does.

`dotnet/` is MedAssist in C#, sharing its data and Foundry agent with the Python version in `examples/medassist/`; both folders' `CLAUDE.md` say what must stay in step. `cd dotnet && dotnet test` runs offline.

Other environments: `python/` lesson scripts use the root `.venv` (`pip install -r python/requirements.txt`). Each folder in `examples/sdks/` has its own Python 3.12 `.venv`, because the SDKs pin conflicting packages; `python examples/sdks/run_all.py [names]` runs them and rewrites `RESULTS.md`. `examples/stack/<area>/<tool>/` works the same way (one `.venv` per tool, `python3 examples/stack/run_all.py [area]`); its `CONVENTIONS.md` is the contract for adding a tool, and `/ai-stack` lists every tool with its result. `examples/claude-agent-sdk/` has one too; the coding agent page (`services/coding.py`) runs its script as a subprocess from that `.venv` when it exists. `examples/tabular/` has one as well (TabPFN needs PyTorch, which the root `.venv` must not get); `services/tabular.py` runs `run_tabular.py` from it, and the `/tabular` page says what to run when it is missing. `examples/lora/` has one too (PyTorch, transformers, peft); `services/lora.py` runs `run_lora.py` from it, one training run at a time, and keeps the downloaded model and the adapters in `generated/lora/`; `lora_data.py` (the task, scoring and memory arithmetic) has no PyTorch, so the backend loads it too. `examples/image-to-3d/` has one too (Idol, from its GitHub repo at a pinned commit); `services/image_to_3d.py` runs `run_idol.py` from it, one object at a time, and keeps each object in `generated/image-to-3d/`. `tools/setup-envs.sh` sets up these environments for a fresh clone (and `check-hf` checks the Hugging Face sign-in and Idol's gated models); a new one goes in its `ENVS` list and the README's "Labs with their own environment" table. Programs the backend starts that run third-party packages get `core/child_env.py`'s environment, never the backend's keys. The coding agent's auto mode runs `bash` under an OS sandbox (`sandbox-exec` on macOS, bubblewrap on Linux, `LLM_LAB_SANDBOX`), or with `LLM_LAB_SANDBOX=docker` in the sandbox image running locally in Docker (`tools/sandbox.sh`, `127.0.0.1:8099`), the usual choice on this machine and each project copy gets its own `.venv`; in Azure it is `LLM_LAB_SANDBOX=sessions`, which sends each command and screenshot to a dynamic session running `examples/coding-sandbox/server.py` (the script loads its `pack`/`unpack` too). `azd up` provisions all the lab's Azure resources, the sandbox included (details in `infra/CLAUDE.md`). `examples/coding-sandbox/setup-app.sh` (one shared container app, Consumption), `setup.sh` (a session pool) and `teardown.sh` create and remove it in Azure. Tests pin the local sandbox, whatever `.env` says. Where no sandbox works, auto mode keeps the full deny rules. Successful installs are recorded in `generated/agent-tools/installed.json`, listed in each new session's `CLAUDE.md`, and shared (a shared venv locally, a set-up step in a cloud session). Keep it that way: agent commands must never run unconfined next to the backend's credentials.

## Backend architecture (`backend/app/`)

The layers (routers, composition root, gateways, services, runs) are described in `backend/CLAUDE.md`. Paid routes: `api/deps.py` holds the two guards they depend on, `require_lab_page` (localhost `Host`/`Origin` plus the `X-LLM-Lab: 1` header, which forces a CORS preflight the server never approves) and `require_budget`. New paid routes need both.

**Shared with the lesson scripts:** `backend/app/shared.py` puts `python/` on `sys.path` and imports `common` (model list, prices, refusal-fallback routing), `settings` and `data` (sample handbook). The harness, skills and coding services run `python/11_harness_loop.py`, `12_agent_skills.py` and `19_coding_agent.py` themselves, through `importlib`. Change prices or models in `python/common.py` only (Claude's and GPT's); there is no second copy. The one exception is `/model-failover`: its pools, their order, windows and compaction model come from `config/model-failover.json` or Table Storage through `ModelCatalogRepository` (`services/model_catalog.py`), and a GPT or local entry may carry its own prices for a model `common.py` does not list (a Claude entry must be one of the lab's Claude models, at its list price). No model name is written in that service or page. `shared.py` also loads `examples/medassist/clinic.py` (MedAssist's practice database, rules and tool loop), so the MedAssist page and that example's command line share one implementation. It loads `examples/aftercare/ward.py` (Aftercare's record, rules and tools) the same way, for the `/aftercare` page, `aftercare.py` (Claude) and `aftercare_af.py` (Agent Framework).

**Environment variables are read only in `python/settings.py`** (`EnvSettings`, which also loads `.env`). Scripts use `settings.ENV`; the backend's `Settings.from_env()` copies from a fresh `EnvSettings`, and services get values from `Settings`, never `os.environ`. A new variable goes in `EnvSettings` first, then in `.env.example` (committed: local defaults set, Azure values, keys and personal values as commented-out placeholders; `test_env_example.py` checks it). The standalone `examples/` projects keep their own config.

The site builder writes into `sites/<id>/site/` through file tools confined to that folder, and `main.py` serves the sites sandboxed (CSP `sandbox`) at `/sites/<id>/`. `sites/`, `casework/` (audit logs), `models/`, `skill_outputs/` and `generated/` (memory stores in `generated/memory-stores/`, each change a version file; the AI-103 labs' photos, video and cached extractions, the data agent's warehouse and dashboards, the coding agent's project copies, the model failover lab's conversations when no Azure Storage is set, and `transcripts/`: every conversation's lines, appended as they are said, and databases copied before a reset) are gitignored runtime data. Routes that serve media to `<img>` or `<video>` tags sit on a separate router without `require_lab_page`, because those requests cannot send the lab header; they only serve files already made.

## Conventions

- Writing on pages, in docs and in code comments is plain British English: short sentences, says what something does and why, no marketing tone. Match the existing docstring style (a one-line summary that explains intent).
- Claude model ids are `claude-haiku-5-5` (default), `claude-sonnet-5-5` and `claude-opus-5-5`; the backend rejects any other model. With `LLM_LAB_LOCAL_MODEL` set, an open model in Docker Model Runner (`tools/local-model.sh`) is also accepted and becomes `DEFAULT_MODEL`. `python/local_model.py`'s `LabClient` (from `make_client()`) sends its requests to the local server's Anthropic-compatible API and refuses Claude-only features (server tools, files, containers, PDFs, MCP) with `NeedsClaude`. The same client sends requests for a GPT chat deployment (`GPT_MODELS`, from `AZURE_OPENAI_DEPLOYMENTS`) to Azure OpenAI through `python/gpt_model.py`, which translates requests, replies and stream events between Claude's shapes and Chat Completions; GPT models are offered last in `MODELS`, never as the default. Server errors on either path raise `ModelUnavailable`. Work that needs Claude-only features defaults to `CLAUDE_MODEL`, and its pages offer `claude_models` from the status. `backend/tests/conftest.py` clears the local model and the GPT deployments, so tests always see Claude defaults; `test_gpt_model.py` uses a fake Azure OpenAI client. Page messages that name the model use `frontend/src/lib/models.ts`. Live translation for calls and texts is `python/translator.py` (Azure Translator through the AI Services account, keyless; its `LANGUAGES` table holds the voices, checked against Azure): fixed wording is translated from reviewed English, every non-English line is kept with an English copy, and the phone lines screen for emergencies in the caller's words and in English. Every page's calls go through `services/lab_failover.py`'s `FailoverGateway` (`LLM_LAB_FAILOVER`, on by default): a call to a model in the failover catalog that fails with 429, 529, 5xx or a timeout moves to the next one, through the one `ModelRouter` the container builds, whose breakers `/model-failover` shares (that page gets the gateway underneath, as it routes its own calls). A model outside the catalog is called as asked; code that drives the SDK client directly (coding agent, harness, skills, decks) keeps the client's one-step `fallback_model()` (`LLM_LAB_RATE_LIMIT_FALLBACK`). `SpendTracker.charge` prices a reply by the model that answered. Skills and decks run on Claude in Anthropic's container, and on GPT or the local model in the coding agent's sandbox through `python/sandbox_skills.py` (workspaces in `generated/skill-runs/`, our own skills in `python/skills/`, files registered by path in `MadeFiles`); the status's `skills_models` lists what those pages offer. Skill scripts travel with each command, so changing them needs no new sandbox image.
- Azure resources are keyless (Entra sign-in through `az login`); don't add key-based paths except where one already exists (Azure Speech).
- `python/analysis_project/` is the coding agent's empty workspace for a person's own files (`inputs/`, `outputs/`, its own `CLAUDE.example.md`); `python/analysis_samples/` holds an invented workbook to try it with.
- `python/coding_project/` is the coding agent's practice project. Its bugs and failing tests are deliberate; leave them. Its instructions are `CLAUDE.example.md`, renamed to `CLAUDE.md` only in the copies the agent works on.
- `examples/claude-code/` holds Claude Code config under names Claude Code does not load (`CLAUDE.example.md`, `dot-claude/`). They are lesson material, not settings for this repo.
