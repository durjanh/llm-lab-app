# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

LLM Lab: interactive pages that show how LLMs and the systems around them work. A FastAPI backend (`backend/`) proxies live Claude and Azure calls behind a spending cap; a React + TypeScript frontend (`frontend/`, Vite) has one route per lab. `README.md` is the full reference; keep it in step when routes, labs or setup change.

## Commands

Run everything from the repo root, with the virtual environment active (`source .venv/bin/activate`; use `python3` before that on macOS).

```sh
python -m backend --budget 1 --reload   # backend on 127.0.0.1:8000, restarts on changes in backend/ and python/
cd frontend && npm run dev              # Vite on :5173, proxies /api, /models and /sites/ to :8000

pytest backend                                          # all backend tests (fake Claude client: no key, no cost)
pytest backend/tests/test_api.py::test_status_reports_models_and_spend   # one test
cd frontend && npm run typecheck        # TypeScript only
cd frontend && npm run build            # typecheck + production build into frontend/dist (served by the backend on :8000)
cd frontend && npm run format           # Prettier: 120 columns, single quotes
```

`pytest` must run from the repo root, because tests import `backend.app...`. There is no Python linter configured.

`dotnet/` is MedAssist in C# (.NET 10, `MedAssist.sln`), in layers that only reach down through interfaces: `MedAssist.Api` (controllers, same `/api/medassist` routes and JSON as the Python backend; `LLM_LAB_MEDASSIST_API=http://127.0.0.1:5080` makes Vite send the page's MedAssist calls there) and `MedAssist.Cli` -> `MedAssist.Application` (services) -> `MedAssist.Domain` (rules, tools, repository ports; no packages), `MedAssist.Data` (SQLite) and `MedAssist.Integrations.Foundry` (both engines: `prompt-agent` and `agent-framework`, chosen by `MedAssist:Engine`). Settings are `appsettings.json` plus the git-ignored `dotnet/appsettings.Local.json`. It shares `examples/medassist/data/medassist.db`, `knowledge/` and the Foundry agent with the Python version, so a change to `clinic.py`'s data, schema or rules must be made in `PracticeData.cs`/`PracticeSchema.cs`/`PatientSession.cs` too; a test pins the database to Python's for a fixed day. `cd dotnet && dotnet test` runs offline.

Other environments: `python/` lesson scripts use the root `.venv` (`pip install -r python/requirements.txt`). Each folder in `examples/sdks/` has its own Python 3.12 `.venv`, because the SDKs pin conflicting packages; `python examples/sdks/run_all.py [names]` runs them and rewrites `RESULTS.md`. `examples/claude-agent-sdk/` has one too; the coding agent page (`services/coding.py`) runs its script as a subprocess from that `.venv` when it exists. The coding agent's auto mode runs `bash` under an OS sandbox (`sandbox-exec` on macOS, bubblewrap on Linux, `LLM_LAB_SANDBOX`), or with `LLM_LAB_SANDBOX=docker` in the sandbox image running locally in Docker (`tools/sandbox.sh`, `127.0.0.1:8099`), the usual choice on this machine and each project copy gets its own `.venv`; in Azure it is `LLM_LAB_SANDBOX=sessions`, which sends each command and screenshot to a dynamic session running `examples/coding-sandbox/server.py` (the script loads its `pack`/`unpack` too). `azd up` (`azure.yaml`, `infra/`) provisions all the lab's Azure resources, the sandbox included, and writes `.env` through `infra/hooks/write_env.py` (everything but `LLM_LAB_SANDBOX`, which stays the person's choice); `azd down --purge` removes them. `.github/workflows/infra.yml` runs `azd provision` and `examples/foundry-cicd/eval_gate.py` on main, as the identity `infra/pipeline.sh` makes; in the pipeline the hooks skip Entra and `.env`, and the person's id is `LAB_PRINCIPAL_ID` (azd sets `AZURE_PRINCIPAL_ID` to whoever is signed in). `examples/coding-sandbox/setup-app.sh` (one shared container app, Consumption), `setup.sh` (a session pool) and `teardown.sh` create and remove it in Azure. Tests pin the local sandbox, whatever `.env` says. Where no sandbox works, auto mode keeps the full deny rules. Successful installs are recorded in `generated/agent-tools/installed.json`, listed in each new session's `CLAUDE.md`, and shared (a shared venv locally, a set-up step in a cloud session). Keep it that way: agent commands must never run unconfined next to the backend's credentials.

## Backend architecture (`backend/app/`)

Layered, with one composition root:

- `api/<area>.py`: thin routers (parse, call a service, shape the response), collected in `api/__init__.py` under `/api`. Routes get services only through `api/deps.py`, never by building them.
- `api/deps.py` also holds the two guards paid routes depend on: `require_lab_page` (localhost `Host`/`Origin` plus the `X-LLM-Lab: 1` header, which forces a CORS preflight the server never approves) and `require_budget`. New paid routes need both.
- `container.py`: `Container.build` constructs every service once. `main.create_app(settings, client, browser, speech, gpt, search, foundry, language, agents, tools)` takes optional fakes, which is how tests replace Claude, Chrome, Azure Speech, Azure OpenAI, Azure Search, the Foundry agent, Azure Language, Microsoft Agent Framework and the Foundry Tools gateway (`gateways/foundry_tools.py`: Content Safety, Translator, Content Understanding, gpt-image-2, models with images, and read-only Resource Manager calls, used by the AI-103 labs).
- `gateways/`: the only code that touches external SDKs (`claude.py` for Anthropic, `azure_*.py`, `foundry_agent.py` and `agent_framework.py` with Entra/`az login` sign-in, `browser.py` driving Chrome over DevTools). Services depend on their small protocols.
- `services/`: the work. Every reply is charged to `SpendTracker`. The coding agent (`19_coding_agent.py`) runs on Claude or on a GPT deployment: it keeps the conversation in Claude's format and `to_chat`/`from_chat` translate each GPT call. Long-running work (harness, skills, decks, sites, tutor) runs in a background thread as a `Run` (`services/runs.py`): the worker publishes events, `RunStreamer` sends them to the page as NDJSON, and approval requests wait on the run until the page answers.
- `settings.py`: limits and config, read from the environment. `__main__.py` turns its CLI flags into `LLM_LAB_PORT`/`LLM_LAB_BUDGET` env vars so `--reload` workers see them.
- `core/errors.py`: `ApiError` and the mapping from SDK failures to `{error: {type, message}}` responses.

**Shared with the lesson scripts:** `backend/app/shared.py` puts `python/` on `sys.path` and imports `common` (model list, prices, refusal-fallback routing), `settings` and `data` (sample handbook). The harness, skills and coding services run `python/11_harness_loop.py`, `12_agent_skills.py` and `19_coding_agent.py` themselves, through `importlib`. Change prices or models in `python/common.py` only (Claude's and GPT's); there is no second copy. `shared.py` also loads `examples/medassist/clinic.py` (MedAssist's practice database, rules and tool loop), so the MedAssist page and that example's command line share one implementation. It loads `examples/aftercare/ward.py` (Aftercare's record, rules and tools) the same way, for the `/aftercare` page, `aftercare.py` (Claude) and `aftercare_af.py` (Agent Framework).

**Environment variables are read only in `python/settings.py`** (`EnvSettings`, which also loads `.env`). Scripts use `settings.ENV`; the backend's `Settings.from_env()` copies from a fresh `EnvSettings`, and services get values from `Settings`, never `os.environ`. A new variable goes in `EnvSettings` first. `backend/__main__.py` writes `LLM_LAB_PORT`/`LLM_LAB_BUDGET` so `--reload` workers see the CLI flags. The standalone `examples/` projects keep their own config.

The site builder writes into `sites/<id>/site/` through file tools confined to that folder, and `main.py` serves the sites sandboxed (CSP `sandbox`) at `/sites/<id>/`. `sites/`, `casework/` (audit logs), `models/`, `skill_outputs/` and `generated/` (the AI-103 labs' photos, video and cached extractions, the data agent's warehouse and dashboards, the coding agent's project copies, and `transcripts/`: every conversation's lines, appended as they are said, and databases copied before a reset) are gitignored runtime data. Routes that serve media to `<img>` or `<video>` tags sit on a separate router without `require_lab_page`, because those requests cannot send the lab header; they only serve files already made.

## Frontend architecture (`frontend/src/`)

- `pages/registry.ts` is the single list of pages (id, route, title, nav label, group, body class, lazy component). Nav and routes are generated from it. To add a page: create `pages/<id>/<Name>Page.tsx` with a `<main className="page-<id>">` root, then add it to `PAGES`.
- Many pages keep their interactive parts (simulations, SVG charts, in-browser models) in a plain-JS `engine.js` exporting `mount(root, life)`, started by `useEngine(rootRef, mount)` (`lib/useEngine.ts`, `lib/lifecycle.ts`). These page components never re-render, so React does not redraw over what the script drew. Any listener on `document`/`window` or timer must go through `life.on`, `life.setTimeout` or `life.requestAnimationFrame` so it stops on navigation. New interactive code is TypeScript.
- Each page's CSS is scoped under `.page-<id>` so pages cannot restyle each other; the transformer page uses `body.tx` instead.
- All backend calls go through `services/apiClient.ts` (`ApiClient`): it adds the `x-llm-lab` header, turns failures into `ApiError` with the server's message, and reads NDJSON streams. Add a `services/<area>Service.ts` rather than calling axios from a page.
- Browser models (GPT-2, embedder, reranker in `lib/`) load transformers.js from jsDelivr; the full-internals GPT-2 is served from `models/gpt2-explainer/` (rebuilt by `tools/`).

## Conventions

- Writing on pages, in docs and in code comments is plain British English: short sentences, says what something does and why, no marketing tone. Match the existing docstring style (a one-line summary that explains intent).
- Claude model ids are `claude-haiku-5-5` (default), `claude-sonnet-5-5` and `claude-opus-5-5`; the backend rejects any other model. With `LLM_LAB_LOCAL_MODEL` set, an open model in Docker Model Runner (`tools/local-model.sh`) is also accepted and becomes `DEFAULT_MODEL`. `python/local_model.py`'s `LabClient` (from `make_client()`) sends its requests to the local server's Anthropic-compatible API and refuses Claude-only features (server tools, files, containers, PDFs, MCP) with `NeedsClaude`. The same client sends requests for a GPT chat deployment (`GPT_MODELS`, from `AZURE_OPENAI_DEPLOYMENTS`) to Azure OpenAI through `python/gpt_model.py`, which translates requests, replies and stream events between Claude's shapes and Chat Completions; GPT models are offered last in `MODELS`, never as the default. Server errors on either path raise `ModelUnavailable`. Work that needs Claude-only features defaults to `CLAUDE_MODEL`, and its pages offer `claude_models` from the status. `backend/tests/conftest.py` clears the local model and the GPT deployments, so tests always see Claude defaults; `test_gpt_model.py` uses a fake Azure OpenAI client. Page messages that name the model use `frontend/src/lib/models.ts`. Live translation for calls and texts is `python/translator.py` (Azure Translator through the AI Services account, keyless; its `LANGUAGES` table holds the voices, checked against Azure): fixed wording is translated from reviewed English, every non-English line is kept with an English copy, and the phone lines screen for emergencies in the caller's words and in English. A request rate limited or overloaded (429, 529) after the SDK's retries is sent once to `fallback_model()` (`LLM_LAB_RATE_LIMIT_FALLBACK`), and `SpendTracker.charge` prices a reply by the model that answered. Skills and decks run on Claude in Anthropic's container, and on GPT or the local model in the coding agent's sandbox through `python/sandbox_skills.py` (workspaces in `generated/skill-runs/`, our own skills in `python/skills/`, files registered by path in `MadeFiles`); the status's `skills_models` lists what those pages offer. Skill scripts travel with each command, so changing them needs no new sandbox image.
- Azure resources are keyless (Entra sign-in through `az login`); don't add key-based paths except where one already exists (Azure Speech).
- `python/analysis_project/` is the coding agent's empty workspace for a person's own files (`inputs/`, `outputs/`, its own `CLAUDE.example.md`); `python/analysis_samples/` holds an invented workbook to try it with.
- `python/coding_project/` is the coding agent's practice project. Its bugs and failing tests are deliberate; leave them. Its instructions are `CLAUDE.example.md`, renamed to `CLAUDE.md` only in the copies the agent works on.
- `examples/claude-code/` holds Claude Code config under names Claude Code does not load (`CLAUDE.example.md`, `dot-claude/`). They are lesson material, not settings for this repo.
