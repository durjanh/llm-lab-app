Where the time and money go

Three mechanics explain most LLM latency and cost: the model reads your prompt in one fast pass and then writes the answer one token at a time; a cache keeps it from re-reading old tokens; and every API call resends the whole conversation.

1. Reading is fast, writing is slow

Generation has two phases. Prefill processes the whole prompt in parallel. Decode then produces output tokens strictly one after another. The speeds below are illustrative starting values; measure your own provider and model.

2. The KV cache: don't re-read what you've read

To write each new token, attention needs the keys and values of every earlier token. Without a cache the model would recompute them all at every step. With the KV cache it stores them once and only processes the newest token. Each row below is one decode step; dark cells are tokens processed in that step.

The cache costs memory, and that limits serving

The KV cache grows with every token in context. For models you host, it is often what limits how many users or how long a context one GPU can serve. Models with grouped-query attention share keys and values across heads to shrink it.

3. Every call resends the whole conversation

APIs are stateless. On turn 20 of a chat or an agent loop, you send the system prompt, the tool definitions and all 19 previous turns again. Input per call grows every turn, so total cost grows roughly with the square of the number of turns. Prompt caching bills the repeated prefix at a fraction of the price.

Engineering takeaways

  • Output length drives latency. Writing is far slower than reading, so a shorter answer is usually the biggest speed-up. Ask for concise output and set max_tokens deliberately.
  • Stream anything a person waits for. Total time stays the same, but the first words arrive after the time to first token instead of at the end.
  • Put stable content first. Prompt caching matches the exact prefix: tools, then system prompt, then messages. A timestamp or a reordered tool list near the top invalidates everything after it.
  • Check the cache is working. usage.cache_read_input_tokens should be large on repeat calls. If it stays at zero, something in your prefix changes every time.
  • Long sessions need a plan. Summarise or compact old turns, trim large tool results, or retrieve what is needed rather than keeping everything in context.
  • When self-hosting, size for the KV cache. Context length times concurrency, not just model size, decides how much GPU memory you need.
