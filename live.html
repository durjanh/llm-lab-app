The other labs use small local models and estimates. This page sends real requests to Claude through a small server on your machine, then shows what each call actually cost in time and tokens. Your API key stays in the server and never reaches the browser.

2. Effort against quality and spend

Effort controls how hard the model thinks. Run the same question at several effort levels and compare correctness, output tokens, time and cost. Easy questions rarely need high effort; hard ones may.

Bars show output tokens, which is mostly thinking. One run per level is a single sample, so repeat before drawing conclusions.

3. Prompt caching, done right and done wrong

Three separate questions share the same long handbook in the system prompt. Compare three ways of caching it. The explicit breakpoint marks the end of the shared part, so later calls read it from the cache. Automatic caching puts its breakpoint at the end of each request, after the question that changes every time, so it writes a new entry on every call and never reads one back.

Order matters. Caches last about five minutes, and an entry written by one mode can be read by the next. If you run the explicit breakpoint first, automatic caching will find that entry and look as good. To see automatic caching on its own, run it first, or wait five minutes after the last run.

4. Count tokens exactly

The token counting endpoint uses Claude's own tokenizer, so it gives the real number, not an estimate.

Engineering takeaways

  • Measure on your own prompts. Latency, token counts and cost depend heavily on the task, the model and the effort level. Published averages are a starting point at best.
  • Thinking is billed as output. Higher effort means more hidden output tokens, more time and more cost. Use the lowest effort that keeps quality on your eval.
  • Put the cache breakpoint where the shared part ends. For a fixed document with changing questions, mark the system prompt. For a growing conversation, automatic caching works well. Check cache_read_input_tokens to prove it.
  • Keep keys on the server. Never put an API key in browser code. A small backend that holds the key and enforces limits is the pattern this page uses.
  • Set a spending cap while experimenting. The local server stops after a set amount per session, which you choose with --budget.
