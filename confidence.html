When can you trust a model's confidence?

Many systems act on a model's confidence. A support bot might answer on its own when it is sure and pass everything else to a person. That only works if the confidence is honest: when the model says 80%, it should be right about 80% of the time. This lab measures that with GPT-2 on 60 labelled reviews.

Sixty reviews, each with a confidence

Each review goes into a short prompt, and GPT-2's probabilities for the next token being positive or negative are read off. The two are rescaled to add up to 100%. The larger share is the prediction, and that share is the model's confidence. Half the reviews are plain. The rest are hard on purpose: negation, mixed feelings and sarcasm.

Does 70% sure mean 70% right?

A reliability diagram answers that. It groups the reviews by confidence and shows how often the model was right in each group. On a perfectly calibrated model, every bar would reach the dashed diagonal. Bars above the line mean the model is right more often than it claims, so it is underconfident. Bars below the line mean it is overconfident. With two labels the winner always has at least 50%, so the confidence axis starts at 50%.

Calibrate on labelled data

You can often fix calibration without retraining the model. All you need is a small labelled set. Two simple methods work on label probabilities like these.

Temperature scaling divides the model's score gap between the two labels by one number, T, chosen to fit the labelled set. T below 1 makes the model more decisive. T above 1 makes it more cautious. It never changes which label wins, so accuracy stays the same.

Contextual calibration shows the model a content-free review, here "N/A", and divides each label's probability by the probability the model gave that label for "N/A". This removes a built-in lean towards one label. It can change predictions, so accuracy can change too.

Send the unsure cases to a person

Selective prediction turns confidence into a decision. Above the threshold, the model answers on its own. Below it, the case goes to a person. A higher threshold lets fewer errors through but sends more work to people. The curve shows the whole trade-off, so you can pick the point that matches the error rate you can accept.

Calibration makes the threshold mean something. With raw scores, 0.8 is just a number. After calibration, answers with 80% confidence are right about 8 times in 10, so the threshold can be agreed in plain terms with the people who own the risk. Temperature scaling keeps the reviews in almost the same order, so the curve keeps its shape. What changes is the threshold you need to reach a given point on it.

High probability is not the same as being right

Calibration needs labels. A factual answer comes with a probability but no label, so it is tempting to read the probability as truth. Here GPT-2 names the capital of 15 countries. The table shows its top answer, the probability of that whole answer, and whether it is right. Several of these capitals are not the country's best-known city, such as Ottawa, Canberra and Ankara. That is exactly where a model that learned word patterns slips.

A next-token probability says how likely those words are to come next. It does not check the fact. Wrong answers can score as high as right ones, so a single probability cannot tell you whether one answer is true. Measure how often answers at each confidence level are right before you rely on the number.

Engineering takeaways

  • Check calibration before you build rules on confidence. Score a labelled set from your own task and draw a reliability diagram. On this page, changing only the prompt changes how honest the confidence is, so check again after every prompt or model change.
  • Calibrate on held-out data. Temperature scaling fixes overconfidence or underconfidence without changing answers. Contextual calibration removes a lean towards one label. Fit either on one labelled set and measure on another.
  • Choose the threshold from the coverage curve. Decide what error rate you can accept, then read off how much work goes to people. Revisit it when traffic changes.
  • A high probability is not proof. Models can be confidently wrong, especially when a famous answer sits next to the right one. Ground factual answers in documents and check them.
  • No token probabilities? Measure agreement. If your API does not return token probabilities, ask the same question several times. The share of answers that agree is a practical confidence signal. Calibrate it on labelled data like any other score.
  • Check verbal confidence against data. A model that writes "I am 90% sure" is producing more text, not reporting a measured probability. Before you trust such statements, check how often they are right on your own labelled cases.
# Agreement across several answers as a confidence signal
from collections import Counter
from anthropic import Anthropic

client = Anthropic()

def ask(question: str) -> str | None:
    resp = client.messages.create(
        model="claude-opus-5-5",
        max_tokens=16000,
        output_config={"effort": "low"},
        messages=[{"role": "user", "content": f"{question}\nReply with the answer only."}],
    )
    if resp.stop_reason == "refusal":
        return None
    return next(b.text for b in resp.content if b.type == "text").strip().lower()

def answer_with_agreement(question: str, n: int = 5) -> tuple[str | None, float]:
    votes = Counter(a for a in (ask(question) for _ in range(n)) if a is not None)
    if not votes:
        return None, 0.0
    best, count = votes.most_common(1)[0]
    return best, count / n

answer, agreement = answer_with_agreement("What is the capital of Australia?")
if agreement < 0.8:  # pick the cut-off from labelled data, as on this page
    print("Send to human review:", answer, agreement)
else:
    print(answer)
